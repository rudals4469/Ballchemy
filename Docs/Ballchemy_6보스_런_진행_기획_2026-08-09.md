# Ballchemy 6보스 런 진행 기획

> 2026-08-16 보상 기획 변경: 전직·계열·Common T3 보상 설명은 폐기되었다. 모든 Boss는 지급처 가중치에 따라 Value 1/2/3 증강을 제공한다. 최신 성장 기준은 `Ballchemy_증강_시스템_기준_2026-08-16.md`를 따른다.

> 전투 필드 기준: 11열 × 15행 (`Column 0~10`, `Row 0~14`, 중앙 셀 `(5, 7)`). 모든 보스·일반 블록·폭탄·함정·포탈 배치는 이 범위와 각 블록의 `GridSize`를 기준으로 계산한다.
>
> 구현 상태: `BossPatternDefinition`과 고정 패턴 보스 Asset 5종은 11열 × 15행 형식이다. 기존 패턴은 좌우에 빈 열을 하나씩 추가해 중앙 정렬을 유지했다. 하강 웨이브 보스는 고정 패턴을 사용하지 않는다.
>
> 문서 범위: 이 문서는 현재 구현된 보스 전투 프로토타입 6종을 설명한다. 보스 번호를 최종 Stage 번호와 동일하게 해석하지 않는다. 성장 보상은 Stage별 전직 없이 공통 증강 시스템과 Boss 지급처 가중치를 사용한다.

작성일: 2026-08-09

## 확정 방향

- 한 런은 총 6개 스테이지로 구성한다.
- 서로 다른 `BossDefinition` 6개를 준비하고 각 스테이지에 보스 한 명을 배정한다.
- 런을 시작할 때 보스 6명의 순서를 한 번만 무작위로 섞는다.
- 같은 런 안에서는 같은 보스가 중복 출현하지 않는다.
- 스테이지를 다시 방문하거나 방을 이동해도 이미 정해진 보스 순서는 바뀌지 않는다.
- 새 런을 시작할 때만 새로운 순서를 만든다.

## 데이터와 런타임 책임

### BossDefinition

- 보스 한 명의 정적 데이터와 전투 규칙을 가진다.
- 패턴, 공격 목록, 공격 주기, 공격 후 생성 블록 수와 특수 블록 풀을 포함한다.
- 런마다 달라지는 출현 순서는 저장하지 않는다.

### BossCatalog

- 선택 가능한 보스 6명의 정적 풀을 제공한다.
- 에셋에 입력된 순서는 편집 편의를 위한 순서일 뿐 실제 런 출현 순서가 아니다.

### BossRunSequence

- 런 시작 시 `BossCatalog`의 유효한 보스 6명을 복사해 Fisher-Yates 방식으로 섞는다.
- `stageNumber - 1`을 인덱스로 사용해 해당 스테이지의 보스를 반환한다.
- 런 도중 저장과 불러오기가 추가되면 보스 ID 순서를 런 세이브 데이터에 저장한다.
- 보스가 6명 미만이거나 ID가 중복되면 런 시작 단계에서 명확한 오류를 보고한다.
- 보스 6종을 모두 Catalog에 등록하며 한 런에서 중복 없이 전부 등장한다.

## 첫 번째 보스: 전선 지휘관

- 기존 테스트 보스의 정식 이름은 `Frontline Commander`로 사용한다.
- 공이 매우 자주 튀는 기본 반사형 보스로 유지한다.
- 고정 패턴의 방해 블록 위치는 사용하지 않고, 전투 진입마다 파괴 가능 블록 24개와 파괴 불가 블록 10개를 무작위로 다시 배치한다.
- 방해 블록은 주변 8칸 기준 이웃이 최대 1개가 되도록 제한해 큰 사각 덩어리로 뭉치지 않게 한다.
- 하단 진입 영역에서 모든 빈칸이 연결되는 배치만 허용해 공이 갇히는 폐쇄 공간을 만들지 않는다.
- 보스 본체 공격과 선택된 블록 공격을 사용한다.
- 공격할 때마다 일반 또는 특수 블록을 추가한다.
- 스테이지가 높아질수록 한 번에 추가되는 블록 수가 2개씩 증가한다.
- 최종 밸런싱 단계에서는 보스 패턴 블록과 보강 블록의 체력을 높여 장기 반사전을 유도한다.

## 두 번째 보스: 증식 군체

- 출현 스테이지에 따라 서로 떨어진 군체 핵 2~4개가 등장한다.
- 등장 연출 중 3번 증식해 최대 16~32개의 전체 군체 블록으로 전투를 시작한다.
- 증식 한 번마다 현재 살아 있는 각 군체 블록이 상하좌우 빈칸 중 하나를 예약한다.
- 여러 부모가 같은 칸을 예약할 수 없으며, 예약 가능한 칸이 없는 부모는 해당 증식을 건너뛴다.
- 새로 생성된 블록은 같은 증식 중 연쇄 증식하지 않고 다음 증식부터 부모로 참여한다.
- 다음 증식 위치는 빈 그리드 칸에 녹색 점멸 테두리로 표시한다.
- 예약을 만든 부모가 플레이어 공격으로 파괴되면 해당 예약은 취소된다.
- 매 적 턴 기본 1회 증식하며 `군체 핵 직접 공격 → 증식 블록 3개 공격 → 추가 1회 증식` 패턴을 순환한다. 따라서 세 번째 패턴은 총 2회 증식한다.
- 증식은 둘 이상의 기존 블록과 맞닿는 칸을 피하고 군체 중심에서 먼 칸을 우선해 가지처럼 바깥으로 퍼진다.
- 군체 핵은 최상단 행과 좌우 끝 열에는 생성되지 않는다. 이후 증식 블록은 테두리 칸까지 퍼질 수 있다.
- 각 증식 블록은 10% 확률로 특수 블록 풀의 블록으로 변이한다.
- 특수 변이 풀에서는 Gold를 제외하며, 변이 블록도 일반 증식 블록과 같은 체력 계산식을 사용한다.
- 군체 핵만 `RequiredEnemy`이며 모든 핵을 파괴하면 남은 증식 블록을 정리하고 보스를 처치한다.
- 맨 아래 공 이동 줄에는 핵과 증식 블록을 생성하지 않는다.

## 세 번째 보스방: 붕괴 전선

- 보스 본체 없이 총 10웨이브를 버티는 스테이지형 보스방이다.
- 총 10웨이브 동안 플레이어 턴 종료마다 살아 있는 블록이 2~4줄 무작위로 하강한다.
- 매 웨이브는 기존 일반 전투의 블록 패턴 생성기를 그대로 사용하며, 해당 턴의 하강 높이와 같은 2~4줄 높이로 생성한다.
- 하강 웨이브에서는 텔레포트, 회복, 플레이어 체력 감소, 골드 특수 블록을 생성하지 않는다. 블록 수리는 생성될 수 있다.
- 맨 아래 행에 닿은 블록은 블록 1개당 피해 1을 주고 즉시 삭제한다.
- 기존 적 공격 턴 UI에는 문구 없이 남은 웨이브 숫자만 표시한다.
- 블록을 전부 파괴하지 못해도 다음 웨이브가 진행되며 10웨이브 종료 시 남은 블록을 정리하고 클리어한다.
- 일반 적 공격 턴은 사용하지 않고 위험선 관리와 파괴 우선순위 판단을 핵심으로 한다.

## 네 번째 보스: 폭탄 반응로

- 보스 본체는 2×2 크기이며 기본 체력은 500이다. 공이 직접 충돌할 때는 공의 피해량과 관계없이 충돌 1회당 체력이 1 감소한다.
- 보스는 매 턴 2×2 영역이 겹치지 않는 빈 위치로 무작위 이동한다.
- 보스 본체가 존재하는 모든 보스는 2×2 크기로 통일한다.
- 전투 시작 시 클리어 조건에 포함되지 않는 보스방 전용 일반 블록 24개를 무작위 빈칸에 배치해 반사 경로를 만든다. 이후 매 턴 폭탄을 추가할 때 파괴된 수만큼 최대 10개를 보충하며 24개를 넘지 않는다.
- 전투 시작과 매 턴 맵의 빈 공간에 폭탄을 최대 10개 살포한다.
- 폭탄은 체력 5를 가지며 공의 실제 피해량만큼 체력이 감소한다. 파괴되면 같은 행과 열에 십자 폭발 피해를 주고, 폭발로 보스를 맞히면 체력이 20 감소한다. 폭발 순간에만 가로·세로 빨간 선이 빠르게 점멸한다.
- 맵의 무작위 빈칸에 파괴되지 않는 차단 블록 6개를 서로 인접하지 않게 배치한다. 차단 블록은 십자 폭발을 해당 위치에서 끊으며, 보스가 텔레포트할 때도 간격을 유지한 새로운 무작위 빈칸으로 함께 재배치된다.
- 같은 행·열의 다른 폭탄은 폭발 피해로 체력이 감소하며 조건이 맞으면 연쇄 폭발한다.
- 같은 연쇄 폭발에서 보스가 가로축과 세로축 양쪽에 모두 적중하면 `십자 포획`이 발생한다. 추가 피해 20을 주고 다음 보스 공격을 1턴 지연한다.
- 보스는 3턴마다 `기본 피해 2 + 현재 남아 있는 폭탄 수`로 플레이어를 공격한다.
- 세부 배치와 수치는 이후 레벨 디자인 단계에서 조정한다.

## 다섯 번째 보스: 함정술사

- 보스는 조준 가능한 중앙·하단 후보 위치 6~8곳 중 하나로 매 턴 이동하며 같은 위치에 연속으로 머물지 않는다.
- 다음 이동 위치는 플레이어가 발사하기 전에 점멸로 예고한다.
- 보스 본체는 2×2 크기다.
- 전투 시작 시 클리어 조건에 포함되지 않는 보스방 전용 일반 블록 24개를 무작위 빈칸에 배치한다. 이후 매 턴 함정을 추가할 때 파괴된 수만큼 최대 10개를 보충하며 24개를 넘지 않는다.
- 맵에는 파괴되지 않는 지형 블록을 기본 4~6개 배치해 반사 경로를 만들되, 보스 이동 위치·함정 생성 위치·발사선은 막지 않는다.
- 함정은 실제 체력을 가진다. 기본 체력은 `ceil(런 시작 최소 공 개수 × 25%)`이다. 현행 Scene 시작 공 15개에서는 체력 4이며, 최신 목표 시작 공 10개를 적용하면 같은 공식에서 체력 3이 되므로 밸런싱 시 다시 확정한다.
- 전투 시작 시 일반 함정 4개를 배치하고 매 적 턴 최대 2개를 보충한다.
- 살아 있는 함정은 유지하며 전체 동시 존재 수는 최대 10개로 제한한다.
- 생명 공급 함정은 파괴 시 보스 최대·현재 체력을 증가시키며 동시 최대 2개로 제한한다.
- 공 정지 함정은 파괴 시 현재 공의 20%를 다음 발사 한 번 동안 정지시킨다. 최소 1개는 발사할 수 있고 누적 정지는 현재 공의 40%를 넘지 않는다.
- 전이 함정은 파괴 즉시 보스를 다른 후보 위치로 이동시킨다.
- 함정 증식 장치는 파괴 시 생명 공급을 제외한 함정 2개를 생성하며 동시 최대 1개로 제한한다.
- 방벽 함정은 파괴 시 다음 턴까지 보스 주변에 임시 반사 방벽 2개를 생성한다.
- 전투당 1개의 고내구도 `방어 증폭기` 함정을 추가로 배치한다.
- 방어 증폭기의 체력은 `ceil(런 시작 최소 공 개수 × 75%)`이며 현재 기준 체력 12이다.
- 방어 증폭기를 파괴하면 보스에게 `기본 2회 + 현재 스테이지 번호`만큼의 충돌 흡수형 쉴드를 부여한다. 이 수치는 구현 중 조정한다.
- 함정 효과는 접촉이 아니라 파괴 시에만 발동하며, 종류별 색상과 아이콘을 명확히 구분한다.
- 보스방 종료 시 정지된 공, 임시 방벽, 쉴드 및 모든 함정 상태를 정리한다.

## 여섯 번째 보스: 균열 지휘자

- 첫 번째 보스와 유사한 2×2 본체, 일반·파괴 불가 블록 패턴, 기본 공격 순환을 사용한다.
- 고정 패턴의 방해 블록 위치는 사용하지 않고, 전투 진입마다 파괴 가능 블록 20개와 파괴 불가 블록 8개를 간격 제한과 함께 무작위 배치한다.
- 맵의 빈칸에 파괴되지 않는 텔레포트 포탈 6개를 추가 배치한다.
- 포탈을 방해 블록보다 먼저 서로 떨어진 내부 칸에 배치하고, 각 포탈 주변 8칸은 방해 블록 금지 구역으로 유지한다.
- 최종 방해 블록 배치도 모든 빈칸의 연결성을 검사해 공이 갇히는 구조를 폐기한다.
- 포탈은 `A → B → C → D → E → F → A` 형태의 단방향 순환 네트워크로 연결한다.
- 매 적 턴마다 포탈 연결 순서를 무작위로 다시 섞는다.
- 공은 텔레포트 전의 속도와 진행 방향을 유지하며, 출구 포탈을 벗어나기 전에는 같은 포탈에 재진입하지 않는다.
- 공별 성공 텔레포트 횟수는 한 번의 발사 동안 누적하고 발사 종료 시 초기화한다.
- 텔레포트를 0~2회 사용한 공은 보스에게 기본 피해를 주고, 3회 이상 사용한 공은 보스에게만 1.5배 피해를 준다.
- 일반 블록 피해에는 텔레포트 배율을 적용하지 않는다.

## 이번 구현에서 연결한 기반

- 방 맵의 `StageMap.StageNumber`를 현재 런의 기준 스테이지 번호로 사용한다.
- 새 스테이지 맵 초기화 시 `BlockGridManager`와 `BlockWaveDirector`에 번호를 동기화한다.
- 이 동기화는 레거시 `CompleteBossAndStartNextStage()`를 호출하거나 다음 일반 웨이브를 즉시 만들지 않는다.
- 일반 및 네임드 전투방의 블록 수치와 특수 블록 주입은 현재 스테이지 인덱스를 난이도 인덱스로 사용한다.
- 총 스테이지 수 기본값과 현재 씬 설정은 6으로 맞춘다.

1. 확정한 나머지 보스방 4종의 `BossDefinition`과 전용 진행 데이터를 만든다.
2. `BossCatalog.bossPool`에 서로 다른 Boss ID를 가진 보스 6명을 등록한다.
3. 같은 런에서 방 재입장 시 동일 보스가 유지되는지 플레이 모드에서 검증한다.
4. 새 런 시작 시 순서가 다시 섞이는지 플레이 모드에서 검증한다.

## 이번 단계에서 보류한 범위

- 나머지 보스 5명의 구체적인 패턴과 공격 구현
- 보스별 체력 최종 밸런싱
- 런 저장 및 불러오기
- 최신 7 Stage 구조의 Stage 7 최종 보스 처치 후 런 완료 화면
- 기존 웨이브 기반 보스 API 삭제

레거시 API는 아직 다른 참조와 회귀 가능성을 확인해야 하므로 삭제하지 않고, 방 기반 흐름에서 신규 호출만 하지 않는 상태로 유지한다.
